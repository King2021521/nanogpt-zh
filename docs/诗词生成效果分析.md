# 诗词生成效果不佳 - 原因分析与改进建议

@Author xiaomin.zhang

## 现象

- **续写结果**：生成内容多为标点（，。）、单字或重复片段，语义不通，与原文差距大。
- **困惑度**：约 7.94，说明模型学到了一些规律，但远未学好。

## 原因分析

### 1. 词表与编码方式不一致（主要原因）

- **词表来源**：`scripts/rebuild_vocab.py` 按**字符频率**构建词表，即词表里是**单字**（如「春」「江」「，」「。」）。
- **编码方式**：`utils/tokenizer.py` 的 `encode()` 使用 **jieba 分词**，得到的是**词**（如「春江」「潮水」）。
- **后果**：  
  jieba 切出的多字词在字符级词表中大多不存在，被映射成 **`<UNK>`**。  
  训练时序列里大量是 UNK，模型主要在学习「在 UNK 之后该出什么」，而标点、单字在词表里且出现频繁，所以容易退化成「标点 + 少量单字」的生成。

### 2. 训练与推理的序列分布不一致

- **训练**：DataLoader 使用 `add_special_tokens=True`，序列形如 `[BOS, w1, w2, ..., EOS]`，模型始终在「见过 BOS 或前文」的条件下预测下一个 token。
- **推理**：`quick_generate.py` / `test_poetry.py` 使用 `add_special_tokens=False`，只喂入 `[w1, w2, ...]`，**没有 BOS**。
- **后果**：  
  模型从未在「无 BOS 的纯上文」下做过预测，存在分布偏移，续写时表现会变差。

### 3. 损失未忽略 Padding

- **数据**：短句会被 pad 到 `max_seq_len`，`target_ids` 里包含 `pad_id`（0）。
- **损失**：`models/gpt.py` 中 `cross_entropy(..., ignore_index=-1)`，而 pad 的 id 是 **0**，因此 **padding 位置参与了损失计算**。
- **后果**：  
  模型被鼓励去预测 PAD，浪费容量并干扰对真实诗词 token 的学习。

### 4. 困惑度 7.94 的解读

- 相对随机（困惑度 ≈ 10000）已经好很多，说明确实学到了部分统计规律（如标点、常见单字）。
- 但 7.94 仍偏高，且生成以标点和碎片为主，说明**有效语义 token 的预测仍不准**，与上述编码、分布、损失问题一致。

## 改进建议（按优先级）

| 优先级 | 项 | 说明 |
|--------|----|------|
| 高 | 词表与编码一致 | 若使用 `rebuild_vocab` 的字符级词表，则 encode/decode 应改为**按字符**，不用 jieba。 |
| 高 | 损失忽略 PAD | `cross_entropy` 的 `ignore_index` 设为 `config.pad_id`（0），不把 padding 算进损失。 |
| 高 | 推理时加 BOS | 生成时在 prompt 前加上 BOS，使「第一个 token 的上下文」与训练时一致。 |
| 中 | 训练步数/轮数 | 若仍欠拟合，可适当增加 `max_steps` 或 `max_epochs`，并观察 val loss。 |
| 中 | 生成参数 | 可尝试略降 temperature（如 0.8）、适当 top_k/top_p，减少乱码。 |
| 低 | 标点抑制 | 当前已有 `suppress_punct_tokens`；若修好上述问题后标点仍过多，再微调抑制强度。 |

## 小结

核心问题是：**用字符级词表却按词（jieba）编码**，导致大量 UNK、训练目标被扭曲；再加上**推理不加 BOS** 和 **损失未忽略 PAD**，共同造成「续写以标点和碎片为主、语义差」的现象。  
优先完成：字符级编码与词表一致、损失忽略 PAD、推理时加 BOS；若仍不满意，再考虑加长训练和调节生成参数。
